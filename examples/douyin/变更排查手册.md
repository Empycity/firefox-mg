# 链路变更与算法对比排查手册

本文用于站点接口、签名算法、安全 SDK 或请求字段发生变化时快速定位。原则是：
先确认失败发生在哪一层，再只比较该层，不从头重写整条链路。

## 一、当前稳定基线

当前成功链路顺序：

```text
Cookie/msToken
  -> upload/auth/v5（a_bogus；任务级 __security_mc_* marker）
  -> ApplyUploadInner（AWS V4）
  -> 视频二进制上传（Auth + CRC32）
  -> CommitUploadInner（AWS V4）
  -> video/enable + video/transend（a_bogus）
  -> 封面 Apply/Upload/Commit/Validate
  -> create_v2（a_bogus + 固定 Ticket Guard client data + CSRF + dtrait）
```

验收基线：连续任务全部 `HTTP 200`、业务 `status_code=0` 并返回 `item_id`。

本轮稳定不变量：

```text
msToken query 固定，不写回响应 x-ms-token
bd-ticket-guard-client-data 固定
x-secsdk-csrf-token 固定
x-tt-session-dtrait 固定
REE public key 固定
三枚 __security_mc_* 每个发布任务开始换一次，任务内部保持不变
a_bogus 每个创作者接口动态生成
body 按视频、封面、creation_id 动态变化
```

## 二、按失败阶段定位

| 首个失败阶段 | 主要所属层 | 优先对比对象 |
|---|---|---|
| `upload-auth` | Cookie、msToken、a_bogus、任务级 marker | unsigned URL、query 键集合、Cookie 名集合、三枚 marker 是否存在。 |
| `video-apply` | AWS V4、临时凭证 | canonical query、日期、scope、签名头、`user_id`。 |
| `video-upload` | 存储上传协议 | Apply 返回的 Host/Auth/StoreUri、CRC32、分片 query。 |
| `video-commit` | AWS V4、业务 body | payload hash、SessionKey、Functions。 |
| `video-status` | 创作者签名、转码状态 | Vid、msToken、a_bogus、服务端处理状态。 |
| 封面阶段 | ImageX 签名与上传 | ServiceId、SessionKey、StoreUri、图片 CRC32。 |
| `create-v2` | 最终安全层 | a_bogus、固定 client data、CSRF、dtrait、三枚 marker、body 字段。 |
| 返回成功但作品属性错误 | 业务字段 | visibility、download、timing、media_type、cover。 |

前一个阶段成功意味着它之前的算法和参数大概率仍有效。例如视频上传与转码全部
成功、只在 `create_v2` 失败时，应先检查最终安全头和任务级 marker。

## 三、最小对比样本

准备两条同类型请求：

1. 浏览器页面产生的一条成功请求；
2. 本地程序同接口的一条失败请求。

对比时保留结构，敏感值只记录长度和 SHA-256：

```text
method
path
query 键、顺序、空值、URL 编码
header 键集合及关键值长度/hash
Cookie 名集合
body JSON 结构、字段类型、空值
HTTP 状态、响应长度、业务状态
请求时间与两端系统时间
```

先做结构差异，再看值差异。时间戳、随机串、Vid、StoreUri、SessionKey、签名值
天然不同，不比较结果字节，只比较输入、格式和生成时机。

## 四、各算法关键不变量

### a_bogus

实现入口：`ABogusSigner.sign()`、`signed_creator_url()`、`bdms-runner.js`。

检查：

- `msToken` 必须先加入 unsigned URL；
- 输入 URL 的 query、顺序和编码必须与浏览器一致；
- 每个创作者接口重新生成，历史值不复用；
- `creator-runtime-contract.json` 的 `script_path` 指向随包 BDMS 资源；
- SDK 更新时先替换 `assets/` 资源，再更新环境契约和固定测试向量。

### AWS V4（ImageX/VOD）

实现入口：`sign_aws_v4_request()`、`sign_imagex_request()`。

检查：

- canonical query 是否排序、保留空值并按 RFC 3986 编码；
- payload SHA-256 是否对实际发送字节计算；
- 日期、region、service 和 credential scope；
- 临时 `SessionToken` 是否进入签名头；
- 本机时间偏差；
- ImageX 使用 `imagex` service，VOD 使用 `vod` service。

### Ticket Guard / CSRF / dtrait

实现入口：`LocalSecurityRuntime.headers()`、`更新运行态.py`。

当前稳定规则：

- 优先复用浏览器成功请求导出的 `bd_ticket_guard_client_data_header`；
- `csrf`、`x_tt_session_dtrait`、`ree_public_key` 必须和该 client data 来自同一会话；
- 本地 HMAC 生成 client data 只作为旧快照兼容回退；
- 浏览器三次成功证明这些头可在同一会话内固定复用。

重建时检查：

```text
bd-ticket-guard-client-data len/hash
x-secsdk-csrf-token len/hash
x-tt-session-dtrait len/hash
bd-ticket-guard-ree-public-key len/hash
```

### 三枚 `__security_mc_*`

实现入口：`HttpClient.rotate_security_markers()` 和批量任务循环。

当前稳定规则：

```text
每个发布任务开始轮换一次；
同一任务内部 upload-auth、视频处理、封面、create_v2 保持同一组；
signed_creator_url() 内不轮换。
```

对比浏览器时要同时抓同一任务的 `upload-auth` 和最终 `create_v2`，确认三枚 marker
一致；再比较下一任务是否换新值。

### msToken

实现入口：`signed_creator_url()`、`HttpClient.request()`。

检查：

- 当前 Cookie 中存在 `.bytedance.com` 的 `msToken`；
- query 中的值来自当前 Session；
- 生成 `a_bogus` 前已经加入 URL；
- 响应头 `x-ms-token` 只打印长度/哈希，不覆盖 Cookie；
- 标准 `Set-Cookie` 仍由 Session 正常接收。

### create_v2 body

实现入口：`build_video_create_body()`、`build_create_body()`。

检查字段类型：`text_extra/activity/challenges/mentions` 是 JSON 数组字符串，
`anchor` 是对象。当前视频稳定值：

```text
visibility_type=1
download=1
timing=0
media_type=4
```

封面必须使用已 Commit 并校验通过的 StoreUri。

## 五、修改顺序

1. 保存当前可运行目录副本和一次成功结果摘要；
2. 获取目标接口的一条浏览器成功样本，命中后立即停止采集；
3. 对 query/header/body 做结构化差异；
4. 只修改对应算法模块或契约资源；
5. 增加脱敏日志或固定向量测试；
6. 先运行单视频或三视频验证；
7. 最后运行连续五次脚本；
8. 更新本文、参数来源文档和运行文档，清理临时 JSON、旧日志、profile、
   `__pycache__`。
